# Desktop and Android installation trust

The reported Windows message is **“Windows protected your PC / unknown publisher”**, not a named malware detection. Microsoft SmartScreen can show that for a new or unsigned installer; it is not proof of a virus. It is also not proof the file is safe. Do not disable Defender/SmartScreen or tell validators to bypass institution policy. See [Microsoft's SmartScreen reputation guidance](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation).

## Windows Desktop: current local installer

The earlier `CDM_Frontend/release/CDM Portal Setup 0.1.0.exe` was an incomplete 360 KB stub. It was replaced on 2026-11-16 by a **109,179,497-byte** NSIS installer built from the normal Desktop renderer. `npm run desktop:check-installer` and a 7-Zip NSIS archive integrity check pass. The packaged renderer matches the fresh build and targets `https://api.cdmportal.xyz/api`, **the existing live API**, not the offline demo. SHA-256: `79783625396a8e0fe7c6e3db44a9a1eafcdf55fad25cddc5ac37c7a589574182`.

This is an **unsigned** installer. The build and archive checks do not prove that it installs or runs on a Windows device; test both on the actual presentation PC before relying on it. SmartScreen or institutional policy may still block it. Any actions performed in this app can change live data through the live API, so use only authorized accounts and records. The separate IT-validation API and database have not been provisioned. The builder used its built-in NSIS uninstaller extractor on Linux through `CDM_Frontend/scripts/nsis-uninstaller-without-wine.cjs` because Wine is unavailable; the resulting installer still needs Windows installation testing.

On a connected **Windows build machine** and an approved release revision:

1. Configure a trusted code-signing identity owned by Colegio de Montalban. Inject `WIN_CSC_LINK` and `WIN_CSC_KEY_PASSWORD` (or the supported equivalent) through a secure build environment, never in Git or a frontend `.env` file. The current [electron-builder v26 signing guide](https://www.electron.build/v26/docs/features/code-signing/code-signing-win/) explains these inputs. A self-signed certificate does not solve SmartScreen.
2. Install locked dependencies with `npm ci` in `CDM_Frontend`, set the **test-targeted** Desktop API variables, then run `npm run it:desktop:win:build` on Windows. This checks the test target, builds the renderer and NSIS package, rejects a payload-less `.exe`, and requires verified Windows signatures. Do not distribute if this command fails. The generic `desktop:build` remains available for non-Windows platform packaging; `desktop:win:build` is an unsigned-capable build check only.
3. `npm run desktop:verify-signed` can recheck an existing installer on Windows. It requires a non-empty Authenticode certificate directory and Windows `Get-AuthenticodeSignature` status `Valid` for both the installer and unpacked app executable. Record the printed SHA-256 hash, signing publisher, release revision, and source URL. Test on a clean Windows device before sharing.

Signing establishes publisher identity and integrity; **it does not guarantee an immediate absence of SmartScreen warnings** for a new app. Microsoft's current guidance says reputation may take time to build. If a named Defender malware detection appears instead, stop distribution and [submit the exact file for Microsoft analysis](https://learn.microsoft.com/en-us/defender-xdr/submission-guide/); do not add an antivirus exclusion as a shortcut.

## Android: use a signed release APK, not a debug APK

`CDM_Frontend/android/app/build.gradle` now reads four signing values only from the build environment: `CDM_ANDROID_KEYSTORE_PATH` (absolute path), `CDM_ANDROID_KEYSTORE_PASSWORD`, `CDM_ANDROID_KEY_ALIAS`, and `CDM_ANDROID_KEY_PASSWORD`. A release task fails when they are absent or the keystore file is missing. Keep the keystore outside Git, back it up securely, and use the **same signing key for later updates to the same Android package ID**. Android requires APKs to be signed before installation; a debug key is for development, not a distributable release. See [Android's app-signing guide](https://developer.android.com/studio/publish/app-signing.html).

After the test API is provisioned, build the mobile renderer with `npm run it:mobile:build`, run `npx cap sync android`, then build `assembleRelease` using the four test/release signing values on a machine with Java and Android SDK. Verify the resulting APK with Android SDK `apksigner verify --print-certs`, record its SHA-256 and signer fingerprint, and install on a clean test device. The CI debug APK is a synthetic-API build check, **not** the presentation APK.

The current Android package ID `edu.cdm.portal` and Windows app identity are the same as the normal app. A test package may conflict with an existing installation; use dedicated clean validation devices until distinct test identities are implemented and verified. Android signing does not make Microsoft Edge automatically trust an APK download on Windows; if Edge blocks the APK specifically, capture that separate warning and file hash for diagnosis.

No signing certificate, Android keystore, or security exception was created by these code changes. A complete unsigned Windows installer now exists locally, but publisher trust and successful installation still require verification on Windows. Signed distribution and Android release packaging still require school-owned signing material through a secure build environment.
