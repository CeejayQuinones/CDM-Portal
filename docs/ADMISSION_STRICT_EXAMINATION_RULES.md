## Six-rule requirements matrix

| Rule | Current implementation | Enforcement boundary |
| --- | --- | --- |
| 1. Desktop/laptop at the designated campus site and network | The rules panel states the requirement. The Vue exam route/navigation are Website-only. Laravel returns no active exam session to a `mobile` client and rejects mobile start, save, and submit requests. | CDM client platform is server-validated and bearer tokens are platform-bound. Physical device type and campus presence are **not** proven. No approved campus IP/CIDR configuration exists. |
| 2. Keep the exam tab active | The page observes `visibilitychange` and window `blur`, presents an accessible warning, and tries the existing save operation when an answer is dirty. Route changes require confirmation; reload/close attempts trigger the browser leave guard while the attempt is active. | These events do not terminate an attempt. A blur alone is too ambiguous, and the backend has no approved termination-reason contract. |
| 3. Ended attempts cannot resume | Laravel locks the candidate and session, refuses further writes after finalization, scores only accepted answers, treats null answers as incorrect, and counts finalized sessions. | Supported and server-authoritative. No separate `terminated` state is invented. |
| 4. No unauthorized resources or assistance | The rule is displayed before the exam and requires explicit acknowledgment. | Conduct rule only. The portal does not claim to detect every AI tool, website, external device, conversation, or helper. No webcam, microphone, recording, or spyware feature was added. |
| 5. Timer never pauses; save while connected; finalize at deadline | Session start/deadline are generated by Laravel and returned with `server_now`. Refresh resumes the same deadline. Autosave reports success only after a server response. Late answers are rejected. The scheduled finalizer runs every minute and finalization is idempotent. | Fully authoritative only when the Laravel scheduler is continuously running. The client timer is display-only. |
| 6. Registrar release and one conditional final retake | Unpublished results are redacted. Registrar review is required before publication. A new attempt is allowed only when the latest result is published with outcome `RETAKE` and the snapshotted maximum has not been reached. | Existing policy defaults to two attempts but the UI now displays the server snapshot instead of hardcoding `2`. No automatic publication or frontend-granted retake exists. |

## Existing examination architecture

- `AdmissionWorkflowController` exposes status, start, answer-save, submit, result, and Registrar review endpoints behind Sanctum, client-platform middleware, and Admission role boundaries.
- `AdmissionExamService` is the single lifecycle service. It uses database transactions, locks the authenticated user, scopes session queries through that user's Admission applicant, and locks active sessions for state transitions.
- Starting snapshots the approved question set and normalized exam policy into a UUID session. One active session per person is resumed rather than duplicated.
- Saves require the current revision and an exact match to the assigned snapshot question IDs. A stale tab receives a conflict instead of silently overwriting newer answers.
- Finalization creates one result, marks every accepted answer correct/incorrect, treats unanswered values as incorrect, records a cause, and changes the session to `finalized` in the same transaction.
- `admission:finalize-expired` finalizes overdue active sessions. `routes/console.php` schedules it every minute with overlap prevention.
- `AdmissionResultService` preserves Registrar approval, publication, correction, and override controls. Candidate result payloads expose nothing official until publication.
- The retake decision remains in `AdmissionExamService::eligibility()`, using the first attempt's snapshotted policy and the latest published outcome.

## Implemented safeguards

### Rules and acknowledgment

- A numbered, responsive six-rule panel is shown before an eligible attempt.
- The Start button remains disabled until the candidate checks the acknowledgment.
- Laravel independently requires `rules_acknowledged` to be accepted before calling the existing start service. All normal eligibility, bank readiness, role, attempt, and publication checks still run server-side.
- Acknowledgment is request validation, not a replacement for eligibility and not a new persistent compliance record.

### Platform isolation

- The Website exam route and navigation entry declare `platforms: ['web']`.
- Android and Electron routing therefore cannot open the candidate exam page.
- Laravel denies non-Website start, save, and submit operations even if a caller bypasses the Vue UI.
- A mobile status request remains usable but returns `unsupported_client` and never includes an active session, questions, or answers.
- Admission status and published result routes were not made Website-only.

### Focus and navigation resilience

- Hidden-tab and lost-focus events generate visible `role="alert"` guidance.
- A dirty answer causes an attempt to use the normal revision-checked save endpoint; the UI never labels an unacknowledged request as saved.
- Leaving the Vue route requires confirmation and warns that the server timer continues.
- Reload/close attempts use the browser's standard active-attempt warning.
- No focus event automatically terminates an attempt, and no right-click or arbitrary keyboard blocking was introduced.

### Server lifecycle and timer

- Identity, ownership, active status, revision, assigned questions, position, deadline, and attempt limit remain validated by Laravel.
- Server timestamps define the deadline. Reload, sign-out, disconnection, or client-clock changes do not extend it.
- Save/finalize races serialize through the existing user/session transaction locks.
- Repeated finalization and repeated submit requests return the already-finalized state without creating another result.
- The attempt display now uses `max_attempts` from the session policy snapshot.

## Supported and unsupported browser detection

Supported observable events:

- document visibility changes;
- window focus loss;
- Vue route departure;
- browser reload/close attempts;
- connection/save failures reported by the existing API request.

Not reliably observable or provable in an ordinary browser:

- every native application switch;
- activity on a second device;
- every external website, AI tool, or communication channel;
- another person in the room;
- physical campus location;
- whether a `web` browser is physically a desktop rather than a phone without managed-device attestation.

The implementation reports these limits in the rules panel. It does not make false proctoring claims.

## Campus, device, and schedule gaps

There is no repository configuration for trusted campus CIDRs, designated exam-site identifiers, managed-device attestation, or a separately approved examination window. The existing cycle has application dates and an active/inactive exam policy, but those must not be reinterpreted as a new official exam-site schedule without policy approval.

Reliable campus enforcement needs all of the following before implementation:

1. Registrar/IT-approved campus egress CIDRs and a named site-to-network mapping.
2. Correct trusted-proxy configuration so Laravel uses a verified client IP rather than a spoofable forwarding header.
3. A written exception policy for outages, VPNs, accessibility needs, and approved alternate sites.
4. If physical device assurance is required, a managed kiosk/device-attestation mechanism; user-agent or screen-size checks are insufficient.
5. Approved start/end windows and timezone semantics if examination scheduling is to be stricter than the current active-policy gate.

Until those inputs exist, CDM Portal enforces its trustworthy client boundary but does not claim campus or physical-device proof.

## Result publication and retake verification

- Candidate-facing `published()` returns `{ published: false, result: null }` until the latest result is officially published.
- Publication remains a Registrar action; there is no automatic release path.
- A passing published result yields `PASSED` and denies another attempt.
- A failing first published result yields `RETAKE` only when the snapshotted maximum permits another attempt.
- A failed final attempt yields `FAILED`; an abandoned, active, pending, approved-but-unpublished, or otherwise incomplete first attempt does not independently grant a retake.
- Policy edits after the first attempt do not silently change that candidate's snapshotted duration, threshold, or attempt maximum.

## Backend work requiring separate approval

### Campus/network authorization contract

Add an approved configuration source containing site IDs and CIDRs, validate the resolved request IP after trusted-proxy handling, fail closed for exam writes outside an authorized site/window, and audit the matched site/configuration version. This must be approved and provisioned by campus IT; no ranges were invented here.

### Focus-event termination contract

If policy later authorizes automatic termination, define an idempotent endpoint such as `POST /api/admission/exam/{session}/interruptions` with a client event UUID and an approved event type. Laravel—not the browser—must lock the candidate/session, evaluate the approved trigger sequence, preserve only server-accepted answers, record server receipt/terminal timestamps and an ending reason, finalize once, and return the authoritative terminal payload. Offline retries must use the same UUID.

That phase likely requires approved schema fields or a related event table for interruption IDs, event types, ending reason, and timestamps, plus a defined appeal/false-positive policy. No migration or terminal-state change was created in this phase.

## Manual browser examination UAT

Automated tests and compilation do not replace the following rendered-browser checks:

1. Sign in as an eligible Guest on the Website and verify the six numbered rules in Light, Dark, and System themes at desktop and narrow widths.
2. Confirm Start is disabled before acknowledgment and enabled afterward; inspect keyboard focus order and screen-reader labels.
3. Start an attempt and verify the shown attempt maximum, question count, deadline countdown, and save status match the server response.
4. Answer a question, wait for server confirmation, refresh, and verify the acknowledged answer and original deadline return.
5. Change an answer and immediately try to leave/reload; verify the browser/route warning is shown and no unsent answer is falsely labeled saved.
6. Hide the tab and switch window focus; verify the accessible warning appears and the attempt is not spuriously terminated.
7. Use two Website tabs to create a stale revision and verify the stale tab receives a conflict instead of overwriting the newer answer.
8. Let a disposable test attempt reach its deadline with the Laravel scheduler running; verify finalization occurs without a browser request, late edits fail, and a single result exists.
9. Submit manually twice and verify the operation is idempotent and questions/answers cannot be resumed after finalization.
10. Verify an unpublished result reveals no score/outcome to the Guest; publish through the authorized Registrar Electron workflow and then verify candidate visibility.
11. Verify a published passing result denies retake, a published first `RETAKE` result permits the configured final attempt, and the final failed result denies another attempt.
12. On Android, verify Admission information/result access remains available as authorized, no Entrance Exam navigation appears, and direct start/save/submit calls are denied.
13. In Electron, verify Registrar examination configuration/review/publication still works and candidate exam-taking UI is unavailable.
14. Test mobile-browser behavior explicitly and record the known limitation: without managed-device or network attestation, the server cannot prove that a `web` client is a desktop/laptop at the campus site.

Browser-rendered UAT was not performed in this command-line validation session and remains required before release approval.
