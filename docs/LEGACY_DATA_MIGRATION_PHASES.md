# Legacy Access data migration — phased implementation

This is a proposed migration path, not evidence that CDM Portal has imported school data. The Registrar interview confirms Access personal records and a gradesheet keyed by student number. It does not establish a reliable legacy source for current section enrollments or schedules.

## Phase 1: export inventory (implemented)

An authorized school operator exports a saved Access query to a delimited CSV file. Access exports are source snapshots, not Portal templates filled in by hand. Keep files outside the repository and restrict access to approved staff. Do not send real student data to development machines or commit it to Git.

Run `php artisan legacy:inspect /secure/path/export.csv --entity=students` or `--entity=grades` from the deployed backend environment only when the school has approved access. The command reads the file and reports a SHA-256 checksum, recognized/missing columns, counts of malformed rows, blank fields, and duplicate student/grade keys. It does not query or write the database, stage rows, validate identities or grades, print row contents, or create student-visible records. A successful structural report is **not** approval to import. The duplicate-key counter uses memory proportional to distinct keys; test it on representative export sizes before a full-school run.

The Access query should provide stable student numbers as text (including leading zeros). Student columns recognized by the inspector include student number, first/last name, program/course, curriculum, year level, status, and admission date. The grade export should include student number, academic year, semester, subject code, final grade, remarks, and credited units. Column names can be adjusted after inspecting the real schema; no production record should be guessed or fabricated. The grade result and source reference required by the existing historical-grade validator must be confirmed from official records, not inferred from a numerical grade.

## Phase 2: restricted staging and provisional matching (implemented foundation)

After the export layout is agreed and an authorized operator has secured the CSV, run `php artisan legacy:stage /secure/path/export.csv --entity=students --operator=REFERENCE` (or `--entity=grades`). The command validates the structural report and writes canonicalized rows to `legacy_migration_batches` and `legacy_migration_rows` in bounded transactions of 200 rows. If interrupted, the batch stays `loading`, is not matchable, and can resume from the same unchanged export. A completed export checksum cannot be staged again. Row payloads use Laravel's encrypted-array cast. The new migration must be tested and separately approved before it is ever applied to a persistent or production database. No staging command has been run against such a database as part of this work.

`php artisan legacy:match BATCH_ID` makes provisional exact matches only. Student rows are checked against existing student numbers and configured course/curriculum codes. Grade rows are matched against existing or uniquely staged student numbers, configured academic terms, and exact subject codes within the student's curriculum. Repeated source keys, unknown students or subjects, and missing fields are marked `needs_review`. The Registrar's existing roster-import page has a read-only panel of batch counts and exception reasons. It never shows source names/emails, approves a batch, or imports a record. Source-key hashes and source row numbers permit duplicate detection without indexing personal values.

Run `php artisan legacy:preflight BATCH_ID` after matching. This reuses the existing roster and historical-grade validation rules and changes provisionally matched rows to `ready` or `needs_review`. The report still contains counts and reason codes only. A student row needs the roster-required record reference and fields; a grade row needs a separately supplied `official_result` (`Passed`, `Failed`, or `Incomplete`) and `source_reference`. Neither is inferred from Access remarks or a numerical grade. A grade linked only to a staged student is held as `student_not_imported`. A `ready` row is **not** approved, imported, or student-visible. The preflight is intentionally single-use for each matched batch so its report remains an immutable rehearsal snapshot. No Portal records are created by this command.

**Before any real school import:** obtain a school-approved export column contract, official subject/curriculum equivalency decisions, a source-to-Portal reconciliation, and a verified backup/recovery plan. `matched` means identifiers match provisionally; `ready` means the current importer rules passed during the dry run. Neither means authorized to commit. Never infer `official_result` from a numerical grade or assume Access `remarks` is equivalent. Rows with unknown subjects, missing official result, or missing source reference must be corrected in an authorized source export and staged as a new batch; this version does not include an in-app crosswalk editor.

## Phase 3: controlled import (implemented for fully matched, approved batches)

After a verified backup and reconciliation, Registrar staff can approve a `preflighted` batch only when every row is `ready`. The approval form requires the source SHA-256, exact reconciled row count, signed review reference, and backup/recovery-check reference; staff step-up authentication is required. Approval is recorded on the batch but imports nothing. An authorized server operator then runs `php artisan legacy:commit BATCH_ID --checksum=SHA256`. The command creates inactive student/alumni identities or verified historical grades in resumable transactions of 100 rows, using the existing roster/grade validators again before every write. Staging rows retain batch, source-row, and created-record references; student records receive audit events with batch provenance and historical grades receive grade audit events. A failed chunk rolls back as a unit; the command can be rerun for an approved/importing batch after the issue is resolved. Already imported rows are not replayed. **Committing grades makes them verified and student-visible.** Do not run it on production until the school has independently approved the export and backup.

Existing small-file importers remain available for later corrections. The historical-grade importer now accepts both a canonical `.xlsx` workbook and a CSV with recognized Access-style headers in any order (maximum 200 rows / 2 MB). It requires an explicit `official_result` and `source_reference` and does not infer either from `remarks`. Current-term enrollment stays in the existing application/section/subject workflow unless a reliable legacy source is confirmed and a separate design is approved. Do not promise batch deletion as rollback after records are activated or used.

For the final-defense rehearsal, use synthetic CSV exports and demonstrate `legacy:inspect` → `legacy:stage` → `legacy:match` → `legacy:preflight` → Registrar approval → operator `legacy:commit`. Run it on a disposable local database only. Import student identities first; then stage/match/preflight the grade export, because grades require existing students. If a grade batch was preflighted before students were imported, `legacy:match BATCH_ID` may be run again on that **unapproved** batch, followed by `legacy:preflight BATCH_ID`. A production run still requires school authorization, official field/mapping decisions, reconciliation, a tested backup, and a pilot against the actual Access schema. This feature does not migrate current enrollments or sections.
